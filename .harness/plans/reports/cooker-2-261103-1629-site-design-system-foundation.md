## Outcome

All five phases are done and every acceptance criterion is met. `site/` now runs Tailwind v4
itself, imports `@jjuidev/design-system/tailwind.css` from the vendored tarball, renders the page
inside the package's `ThemeProvider`, follows the design system's layout and conventions, and
carries its own ESLint, Stylelint and Vitest Browser Mode. The root ESLint no longer globs
`site/src`; the root CLI, its tests and its bundle are untouched.

## Bundle size, before and after

| Asset   | Before (raw / gzip)   | After (raw / gzip)    | Change                   |
| ------- | --------------------- | --------------------- | ------------------------ |
| JavaScript | 220,499 B / 68,177 B | 274,361 B / 86,239 B | +53,862 B / +18,062 B |
| CSS       | 54,532 B / 9,098 B   | 43,875 B / 8,056 B   | −10,657 B / −1,042 B  |

The CSS shrank because the site's own Tailwind engine emits only the utilities the page uses,
instead of the design system's precompiled stylesheet. The JavaScript grew, and the growth was
measured, not guessed:

- The theme provider and the design system's theme store: about 12 kB raw (274.36 kB with the
  provider against 262.52 kB with a local stub).
- `tailwind-variants` and `tailwind-merge`, pulled in by the copied
  `utils/tailwind-variants.util.ts`: about 42 kB raw, roughly 13 kB gzip.

**No design system component reaches the bundle.** The bundle carries no `Button`, `Popover`,
`ThemeToggle`, `SkinToggle` or `Logo` code: `focusableWhenDisabled`, `data-starting-style`,
`z-popover` and the compiled class names of every component are absent. What survives is the
`tv()` variant table of the Button, a few hundred bytes, because `createTV()` is a top-level call
that the bundler cannot prove is pure. `@base-ui/react` and `@mantine/hooks` are absent.

The CSS does carry the design system's component styles, about 20 kB of source, because the
package's `tailwind.css` imports `components.css`. That is the package's contract (its decision
0010): the component styles come from the build that produced the component JavaScript, so the
generated names match.

## The pre-paint theme

The design system owns the theme: `ThemeProvider` reads the `jds-theme` cookie, falls back to the
operating system, writes `data-theme` on `<html>`, and follows the system when it changes. The site
does not reimplement any of it.

The script in `site/index.html` runs before the first paint and applies the same rule the provider
applies on mount: the cookie first, then the operating system. The cookie value `dark` or `light`
wins; anything else, including `system:light` and `system:dark`, resolves from the operating
system, exactly as the package's `readStoredTheme` does, which ignores the resolved half of a
`system:` cookie and re-resolves it.

Measured on the built page, with the preview server:

| Case                                   | `data-theme` | body background | body text |
| -------------------------------------- | ------------ | --------------- | --------- |
| OS light                               | light        | `rgb(255, 255, 255)` | `rgb(28, 22, 18)` |
| OS dark                                | dark         | `rgb(28, 22, 18)` | `rgb(249, 246, 242)` |
| OS light, cookie `jds-theme=dark`      | dark         | the dark palette | the dark palette |

The heading renders at 30 px, weight 600 (`text-heading-3xl`), the link at `rgb(122, 61, 98)` in
light and `rgb(225, 169, 213)` in dark (`text-primary`), and the install block on `bg-raised` with a
`border-default`. Screenshots of both themes are at `/tmp/shot/site-light.png` and
`/tmp/shot/site-dark.png`.

## Where this deviates from the plan

1. **The decision record is `0036`, not `0028`.** Numbers 0028 to 0035 already exist in
   `docs/decisions/`. The record is otherwise as the plan describes it.

2. **The site runs ESLint 9.39.5, not the design system's exact combination.** The design system
   pairs `eslint@9.39.5` with `@eslint/js@10.0.1`, and that pair fails under the site's
   `strictPeerDependencies: true`, because `@eslint/js@10.0.1` requires `eslint@^10`. ESLint 10 is
   not an option either: `eslint-plugin-react@7.37.5`, the latest release, caps its peer at
   `eslint@^9.7`. So the site pins `@eslint/js@9.39.5` to match `eslint@9.39.5`. The consequence is
   that the repository now holds two ESLint majors, one per project. My leaning was to keep the
   design system's version, since the port of its config is what the plan asked for, and the two
   projects have separate lockfiles anyway.

3. **The site uses the `typescript-eslint` package, not the design system's split
   `@typescript-eslint/eslint-plugin` and `@typescript-eslint/parser`.** The unified package is
   what this repository already uses, and it satisfies `eslint-plugin-import-x`'s peer on
   `@typescript-eslint/utils` under `strictPeerDependencies`. The rules are the design system's.

4. **`vite.config.ts` needed two small changes** for the site's stricter `tsconfig.json`, which
   has `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` where the design system's does
   not. `filename.split('?')[0]` became `filename.split('?')[0] ?? filename`, and the `css` option
   is now a conditional spread instead of `undefined`, which `exactOptionalPropertyTypes` rejects.
   The plan asked for this to be reported.

5. **The root `eslint.config.mjs` also lists `site/**` in `IGNORED_PATHS`.** The plan only asked to
   remove `site/src` from `SOURCE_FOLDERS`. The extra entry is a guard: ESLint 10 looks the
   configuration up from the linted file's directory, so site files already use the site's own
   configuration and the root's global ignore never applies to them. With ESLint 9, which looks the
   configuration up from the working directory, the root configuration would otherwise lint the
   site with the wrong rules.

6. **`tests/install.test.ts` was updated** to the new page path. The plan did not mention it, and
   the root suite fails without it.

7. **The site's `format` script does not run Prettier.** Prettier stays at the root, as the plan
   requires; the site's script runs `eslint --fix` and `stylelint --fix`, and the root
   `pnpm format` formats the site files too, because the root Prettier configuration is found from
   the file's own directory.

8. **The `lint` script covers `*.{ts,mjs}` at the site root**, so `eslint.config.mjs`,
   `stylelint.config.mjs`, `vite.config.ts`, `vitest.config.ts` and `vitest.setup.ts` are linted.
   The design system's `lint` script does the same.
